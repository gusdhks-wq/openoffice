# HWP/HWPX 검증 보고서 — 2026-10-23

이 보고서는 비식별 요약이다. 원본·문구·파일명·로컬 절대 경로·계정 정보·그림·화면은 포함하지 않는다.
방법과 판정 범위는 [README](README.md)를 따른다. Android·모바일 AI·Drive 기능 구현 보고서가 아니다.

## 단계별 수행 결과

1. 기존 일회성 스크립트를 검토했다. 절대 경로와 실제 문구가 코드에 있었고, 표 미리보기만 비교했으며,
   실패를 기록하고도 프로세스가 성공 종료할 수 있었다. 공개용으로 그대로 옮기지 않았다.
2. `run.mjs`로 비공개 manifest 입력, 저장소 밖 출력 강제, 버전·WASM 확인, 필수 검사 실패 시
   비정상 종료를 구현했다. 저장 전 무편집 왕복을 먼저 비교해 엔진 직렬화 손실과 요청 편집을 구분했다.
3. 표 검증을 모든 행의 셀 텍스트·병합 span 비교로 확대했다. 합성 HWP/HWPX에서 본문 길이를 늘리고
   표의 기존 값을 바꿨다. 첫 실행에서 overwrite=false가 기존 셀을 거부하는 것을 확인했다.
   이는 엔진 오류가 아니라 보호 동작이었다. 시험을 '거부·무변경 확인 → 명시적 overwrite=true → 요청 셀만 변경'으로 고쳤다.
4. 두 합성 형식 모두 재시험 PASS. 없는 본문 대상 거부·무변경도 확인했다.
5. 비공개 실제 HWP 2개를 새 runner로 재시험했다. 무편집 왕복과 본문 수정 왕복 모두 PASS.
   본문·전체 표 셀/병합 정보와 저장 직전 대비 쪽수를 유지했다. 표는 각각 1개와 5개,
   엔진 쪽수는 각각 1쪽과 4쪽이었다. 전 페이지 SVG 생성도 통과했다.
6. 독립 그림 검사에서 두 문서 각각 BinData 2개, 압축 해제한 그림 데이터 해시 다중집합이 같았다.
   앞선 독립 pyhwp 읽기에서도 수정 문구를 확인했다. 압축된 스트림/파일 바이트 동일성을 요구하지 않는다.
7. `ui.mjs`를 별도로 정리했다. 런타임 모듈을 동적으로 불러오는 초기 코드의 CJS/ESM 접근 오류를
   수정하고 재실행했다. 실제 Electron에서 문서 사본 수정, 정규 저장, 원본과 동일한 백업,
   저장 파일 엔진 재열기, PDF 서명 확인이 PASS였다. 독립 PyMuPDF에서 1쪽·수정 문구 확인 및 렌더 생성도 통과했다.
8. 출력 경로를 저장소 안으로 지정한 부정 시험은 종료 코드 2, 존재하지 않는 수정 대상은
   FAIL과 종료 코드 1로 확인했다. 일반 성공은 0이다.

이번 커밋의 범위는 새 검증 폴더뿐이다. 모바일 코드, 제품 명령 계약, 문서 엔진,
기존 XLSX 수정, 공통 findings.md는 포함하지 않는다.
기존 HWP 엔진·표·저장 관련 4개 시험 파일 126개 통과 기록도 있으나, 이는 실제 Android 동작 증거가 아니다.

## 추가 검증 — 레이아웃과 HWPX 견본

- `getPageTextLayout`/`getPageControlLayout`의 모든 페이지 결과 비교를 추가했다. 두 합성 형식과
  비공개 실제 HWP 2개 모두 무편집 및 수정 후 왕복의 표시 속성·좌표 비교를 통과했다.
  좌표 허용 오차는 0.5 CSS px, 텍스트·표 인덱스·span 등은 정확 비교다.
  serializer-local charShapeId/paraShapeId는 제외하며, 해당 API가 내주지 않는 전체 서식은 미검증이다.
- 기존 저장소의 한컴 저장 익명화 HWPX 견본을 저장소 밖 사본으로 시험했다. 표 3개, 1쪽이며
  본문 수정·전체 표/병합 정보·무편집/수정 왕복 레이아웃·원본 보존·전 페이지 SVG 생성 PASS.
  새 바이너리를 커밋하지 않았다. 이는 사용자 실제 HWPX 원본을 찾은 결과가 아니므로 HWP-V04는
  '한컴 HWPX 견본 PASS, 사용자 실제 HWPX 원본 미확보'로 범위를 구분한다.
- 시스템 글꼴 557개 파일의 cmap을 조사했으나 U+F03EC/U+F0A6 대응 글리프를 확인하지 못했다.
  일부 WOFF2는 Python Brotli 확장 미설치로 읽지 못했으므로 '모든 글꼴에 없다'는 단정은 하지 않는다.
  사설 문자를 임의 치환하거나 라이선스 불명 글꼴을 내려받지 않았다. HWP-V01은 미해결이다.
- 좌표 판정기의 허용 오차 경계, 글꼴/본문 변경, 누락 개체, 행/병합 span 변경,
  비정상 숫자 거부를 Node 내장 테스트로 추가했다.

## 모바일 계약 연계 검증 — 2026-10-24 KST

모바일 PR #1의 d502456은 이제 원본과 명령 journal을 유지하는 HWP/HWPX 작업 공간을 구현했다.
계약 위치는 `docs/plans/mobile-hwp.md`다. 지원 명령은
`{id, kind:'replaceText', find, replacement}`이며, 수정 파일 내보내기는 아직 제공하지 않는다.
복구 JSON과 수정 전 원본 내보내기를 수정된 HWP/HWPX 저장으로 판정하지 않는다.

새 `verify-mobile-adapter.mjs`로 이 커밋의 실제 engine/workspace TypeScript를 Node에서 실행했다.
HWP 12개, HWPX 12개 검사 모두 PASS. 본문·표의 교체 재생, journal undo, 원본 불변성,
중복 ID/오래된 대상/모호한 대상 거부, 실패 후 이전 작업 보존을 확인했다.
검토한 원문 해시를 고정하며, 코드 변경 시 자동으로 새 코드가 검증된 것처럼 보고하지 않는다.
이 결과는 Android 실기기·IndexedDB 충돌·Drive/ChatGPT 동기화·수정 바이너리 저장의 증명이 아니다.

특히 기존 section-tails 회귀에는 '엔진이 수정한 구역을 쓰면서 읽었던 바탕쪽을 누락하는'

엔진·PC 저장 코드나 모바일 파일은 이 검증 작업에서 수정하지 않았다.

저장 보존 경계 재확인: section-tails, tab-widths, field-kinds, tracked-changes, save-flow, save-plan의 6개 기존 시험 파일 69개 모두 PASS. 좌표 판정기 5개도 PASS. 이 기존 시험을 모바일에서 실행한 것으로 해석하지 않는다.

## 모바일 수정본 저장 전 직접 재현

합성 문서 전용 `preservation.mts`를 추가했다. 새 보정 로직을 만들지 않고 현재 PC의
`sectionTailsOf/restoreSectionTails`, `newTabsOf/writeTabWidths`를 그대로 불러 비교했다.

| 사례       | 생 export                 | 기존 보존 처리 후                             | 판정                        |
| ---------- | ------------------------- | --------------------------------------------- | --------------------------- |
| HWP 바탕쪽 | 편집 전 1개 → 편집 후 0개 | 1개 복원, 수정 본문·쪽수 재열기 확인          | 손실 재현 및 기존 처리 PASS |
| HWP 새 탭  | 폭 없는 탭 1개            | 폭 없는 탭 0개, 본문 동일·6000 HWPUNIT 재읽기 | 손실 재현 및 기존 처리 PASS |
| HWPX 새 탭 | 폭 없는 탭 1개            | 폭 없는 탭 0개, 본문 동일·6000 HWPUNIT 재읽기 | 손실 재현 및 기존 처리 PASS |

탭 폭은 합성 시험값이며 실제 글꼴 측정 증거가 아니다. 제품 저장에는 화면에서 측정한 폭을 넣어야 한다.
바탕쪽을 포함한 파일을 새로 공개하거나 엔진/PC/모바일 제품 코드를 변경하지 않았다.
메모·필드·수식 캡션·보호 상태의 모바일 end-to-end 검증은 여전히 남아 있다.
첫 tsx CLI 실행은 샌드박스 IPC 파이프 EPERM으로 실행되지 않았으며, Node의 tsx loader로
변경한 실행에서 위 세 사례가 모두 통과했다. 환경 실행 실패를 문서 엔진 실패로 분류하지 않았다.

## 메모·캡션·필드 보존의 음성 사례 추가

`preservation.mts`에 기존 PC 회귀와 같은 합성 저장 상태 사례 5개를 추가해 총 8개 PASS를 확인했다.

- 연결 대상이 남은 메모만 복원하고, 연결 대상이 삭제되거나 번호가 다른 경우 저장 바이트를 그대로 유지한다.
- 원래 수식 식별 정보가 같은 경우에만 캡션을 복원하고, 다른 수식에는 붙이지 않는다.
- 원래 필드의 종류만 복원하며, 필드 식별자가 다르면 저장 바이트를 그대로 유지한다.
- 성공 복원은 해당 본문 스트림의 기대 바이트와 정확 비교하고, 거부 사례는 파일 바이트 무변경을 확인했다.

이 다섯 시험의 evidence는 `synthetic-saved-state-fixture`다. 앞선 세 개의 실제 엔진 export 손실 재현과
구별하며, Android·한컴 재열기·사용자 실제 문서에서의 기능 확인으로 보고하지 않는다.
새 보정 로직이나 모바일 파일 수정 없이 기존 PC 보존 함수만 실행했다. 메모/캡션/필드의
모바일 end-to-end 저장, 보호 문서 처리, 화면 실측 탭 폭은 계속 남은 항목이다.
